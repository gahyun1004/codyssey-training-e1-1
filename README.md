## 1. 미션 소개

개발은 코드를 작성하는 순간이 아니라, 환경을 세팅하는 순간부터 시작됩니다.

이번 미션에서는 개발의 기본 도구인 **리눅스 CLI(터미널)**, **Docker(컨테이너)**, **Git/GitHub(버전 관리 및 협업)**를 직접 사용하여 재현 가능한 개발 워크스테이션을 구축합니다.

개발 워크스테이션의 목적은 다음과 같습니다.

- 코드가 특정 개인의 컴퓨터에서만 동작하는 문제를 줄인다.
- 팀원 누구나 같은 방식으로 실행·배포·디버깅할 수 있도록 한다.
- 로컬 개발 환경을 체계적으로 구성한다.
- 재현 가능한 실행 환경을 공유한다.
- 협업 기반으로 소스코드를 관리한다.

이번 미션에서 수행할 핵심 흐름은 다음과 같습니다.

1. 터미널에서 작업 디렉터리와 파일 권한을 정리한다.
2. Docker를 설치하고 정상 동작 여부를 점검한다.
3. Docker 이미지와 컨테이너를 실행·관리한다.
4. 간단한 웹 서버를 Dockerfile로 컨테이너화한다.
5. 포트 매핑을 통해 웹 서버 접속을 확인한다.
6. 바인드 마운트를 이용해 호스트 파일 변경사항이 컨테이너에 반영되는지 검증한다.
7. Docker 볼륨을 이용해 컨테이너 삭제 후에도 데이터가 유지되는지 검증한다.
8. Git과 GitHub를 설정하고 VSCode와 저장소를 연동한다.
9. 모든 수행 과정과 검증 결과를 README에 기록한다.

단순히 명령어를 따라 입력하는 것이 아니라, 실행 결과인 **로그·접속 화면·데이터 유지 여부**를 통해 핵심 개념을 확인해야 합니다.

또한 다음 구조적 원칙을 설명할 수 있어야 합니다.

- Docker 이미지와 컨테이너의 차이
- 격리된 실행 환경이 필요한 이유
- 포트 매핑이 필요한 이유
- 바인드 마운트와 Docker 볼륨의 역할
- Git과 GitHub의 역할 차이
- 동일한 서비스를 반복 실행해도 같은 결과가 나오도록 만드는 재현성

이 경험은 이후 리눅스 트러블슈팅, CI/CD 파이프라인, 클라우드 배포 및 운영 학습으로 확장됩니다.

## 2. 서울캠퍼스 환경 안내

서울캠퍼스에서는 시스템 보안 정책상 `sudo` 권한 사용이 제한될 수 있습니다. 이 경우 일반적인 방법으로 Docker를 직접 설치하거나 Docker 데몬을 제어하기 어려울 수 있습니다.

이 문제를 해결하기 위해 **OrbStack**을 사용할 수 있습니다.

OrbStack은 Docker Desktop과 유사한 컨테이너 실행 환경을 제공하며, 별도의 `sudo` 권한 없이 컨테이너를 실행하고 관리할 수 있도록 지원합니다.

OrbStack 사용 흐름은 다음과 같습니다.

1. OrbStack 애플리케이션을 실행한다.
2. OrbStack 내부에서 Docker 엔진이 함께 구동된다.
3. 터미널에서는 기존 Docker 명령어를 동일하게 사용한다.

```bash
docker run
docker ps
docker build
```

### 3.2 기술 문서

- 프로젝트 개요 및 미션 목표 요약
- 실행 환경
  - 운영체제
  - 쉘
  - 터미널
  - Docker 버전
  - Git 버전
- 수행 항목 체크리스트
  - 터미널
  - 권한
  - Docker
  - Dockerfile
  - 포트 매핑
  - 바인드 마운트
  - Docker 볼륨
  - Git
  - GitHub
- 검증 방법
  - 어떤 명령어로 무엇을 확인했는지
  - 결과가 저장된 위치 또는 증거 링크
- 트러블슈팅 2건 이상
  - 문제
  - 원인 가설
  - 확인 과정
  - 해결 방법 또는 대안
- 기술 문서만 읽어도 전체 수행 내용을 파악할 수 있도록 작성한다.
- 기술 문서의 명령어와 출력 결과는 코드 블록으로 정리한다.

### 3.3 터미널 조작 로그

터미널에서 수행한 핵심 명령어와 출력 결과를 기술 문서에 기록한다.

### 3.4 Docker 운영 및 검증 로그

다음 명령어의 실행 흔적과 결과를 기록한다.

```bash
docker --version
docker info
docker images
docker ps
docker ps -a
docker logs <container_name>
docker stats
```

### 3.5 Dockerfile 기반 웹 서버 컨테이너

다음 산출물을 포함한다.

- 웹 서버 소스코드 디렉터리
  - 예: `app/` 또는 `src/`
- 직접 작성한 `Dockerfile`
- 이미지 빌드 명령과 결과
- 컨테이너 실행 명령과 결과
- 포트 매핑 접속 성공 증거
  - 브라우저 화면 또는 로그

### 3.6 포트 매핑 접속 증거

다음 형식으로 컨테이너를 실행한 뒤 접속 성공을 증명한다.

```bash
docker run -p <host_port>:<container_port> <image_name>
```

증거에는 다음 항목이 함께 보여야 한다.

- 브라우저 주소창
- 포트 번호
- 응답 화면

브라우저 대신 `curl` 응답을 사용할 수도 있다.

### 3.7 바인드 마운트 및 볼륨 영속성 증거

#### 바인드 마운트

- 실행 명령을 기록한다.
- 호스트 파일 변경 전과 변경 후를 비교한다.
- 호스트의 변경사항이 컨테이너에 반영되는지 확인한다.

#### Docker 볼륨

- 볼륨 생성 명령을 기록한다.
- 컨테이너 연결 명령을 기록한다.
- 데이터 생성 및 확인 명령을 기록한다.
- 컨테이너 삭제 전과 삭제 후를 비교한다.
- 새 컨테이너에 같은 볼륨을 연결했을 때 데이터가 유지되는지 증명한다.

### 3.8 Git 및 GitHub/VSCode 연동 증거

- Git 사용자 정보를 설정한다.
- Git 기본 브랜치를 설정한다.
- VSCode에서 GitHub에 로그인한다.
- VSCode와 GitHub 저장소를 연동한다.
- `git config --list` 결과를 기록한다.
- 연동 완료 화면 또는 로그를 README에 첨부한다.
- ID, 비밀번호, 토큰 등 민감정보가 노출되지 않도록 한다.

## 4. 과제 목표

미션 완료 후 다음 내용을 스스로 설명할 수 있어야 합니다.

### 4.1 경로

- 절대 경로와 상대 경로의 차이를 설명할 수 있다.
- 실제 디렉터리 예시를 들어 두 경로를 구분할 수 있다.

### 4.2 파일 권한

- 파일 권한 `r`, `w`, `x`의 의미를 설명할 수 있다.
- 사용자, 그룹, 기타 사용자의 권한 구조를 설명할 수 있다.
- `755`, `644`와 같은 숫자 권한 표기가 어떻게 계산되는지 설명할 수 있다.

### 4.3 Dockerfile과 커스텀 이미지

- 기존 Docker 이미지를 베이스 이미지로 사용하는 이유를 설명할 수 있다.
- 기존 Dockerfile 또는 베이스 이미지를 기반으로 커스텀 이미지를 만들 수 있다.

### 4.4 포트 매핑

- 호스트 포트와 컨테이너 포트의 차이를 설명할 수 있다.
- 외부에서 컨테이너 서비스에 접속하려면 포트 매핑이 필요한 이유를 설명할 수 있다.

### 4.5 Docker 볼륨

- 컨테이너가 삭제되면 기본 파일 시스템의 데이터가 사라질 수 있음을 설명할 수 있다.
- Docker 볼륨을 이용해 데이터를 영속적으로 보관하는 방법을 설명할 수 있다.

### 4.6 Git과 GitHub

- Git은 로컬 버전 관리 도구임을 설명할 수 있다.
- GitHub는 원격 저장소 및 협업 플랫폼임을 설명할 수 있다.
- Git과 GitHub의 역할 차이를 설명할 수 있다.

## 5. 기능 요구 사항

모든 요구사항을 충족해야 합니다.

### 5.1 제출 저장소 및 기술 문서

- GitHub Repository 링크로 제출한다.
- 모든 수행 결과는 README 또는 README에서 연결되는 문서에서 확인할 수 있어야 한다.
- README에 다음 내용을 반드시 포함한다.
  - 프로젝트 개요
  - 실행 환경
  - 수행 항목 체크리스트
  - 검증 방법
  - 결과 위치 또는 증거 링크
- 명령어와 출력 결과는 코드 블록으로 정리한다.

### 5.2 터미널 조작 로그 기록

다음 작업을 터미널에서 수행하고 명령어와 출력 결과를 기록한다.

- 현재 위치 확인
- 디렉터리 목록 확인
- 숨김 파일을 포함한 목록 확인
- 디렉터리 이동
- 디렉터리 생성
- 파일 생성
- 파일 복사
- 파일 또는 디렉터리 이동
- 파일 또는 디렉터리 이름 변경
- 파일 또는 디렉터리 삭제
- 파일 내용 확인
- 빈 파일 생성

예시 명령어:

```bash
pwd
ls
ls -la
cd
mkdir
cp
mv
rm
cat
touch
```

### 5.3 권한 실습 및 증거 기록

- 파일 권한을 확인한다.
- 파일 권한을 변경한다.
- 변경 전과 변경 후를 비교한다.
- 파일 최소 1개에 대해 권한 변경을 수행한다.
- 디렉터리 최소 1개에 대해 권한 변경을 수행한다.
- 수행 명령과 출력 결과를 README에 기록한다.

예시 명령어:

```bash
ls -l
chmod 644 <file>
chmod 755 <directory>
```

### 5.4 Docker 설치 및 기본 점검

- Docker 버전을 확인한다.
- Docker 데몬 또는 Docker 엔진의 동작 여부를 확인한다.
- 실행 결과를 README에 기록한다.

```bash
docker --version
docker info
```

### 5.5 Docker 기본 운영 명령 수행

#### 이미지

- Docker 이미지를 다운로드한다.
- 이미지 목록을 확인한다.


- 컨테이너를 실행한다.
- 실행 중인 컨테이너를 확인한다.
- 전체 컨테이너를 확인한다.
- 컨테이너를 중지한다.

```bash
docker run <image>
docker ps
docker ps -a
docker stop <container>
```

#### 운영

- 컨테이너 로그를 확인한다.
- 컨테이너 리소스 사용량을 확인한다.

```bash
docker logs <container>
docker stats
```

모든 수행 명령과 출력 결과를 기술 문서에 남긴다.

### 5.6 컨테이너 실행 실습

- 실행 결과를 기록한다.


#### 컨테이너 접속 방식 관찰

### 5.7 기존 Dockerfile 기반 커스텀 이미지 제작

아래 두 방식 중 하나를 선택한다.

#### 방식 A: 웹 서버 베이스 이미지

- NGINX 또는 Apache 등의 웹 서버 이미지를 사용한다.
- 정적 콘텐츠 또는 설정을 교체한다.

#### 방식 B: Linux 베이스 이미지

- Ubuntu 또는 Alpine 등의 Linux 이미지를 사용한다.
- 다음 중 필요한 기능을 추가한다.
  - 패키지
  - 사용자
  - 환경 변수
  - 헬스체크

제작 결과는 다음 조건을 충족해야 한다.

- 커스텀 이미지 빌드 성공
- 커스텀 컨테이너 실행 성공
- README에 선택한 베이스 이미지 또는 예시 Dockerfile을 기록
- 각 커스텀 포인트의 목적을 기록
- 빌드 명령과 핵심 결과를 기록
- 실행 명령과 핵심 결과를 기록
- 필요한 경우 출력 화면 또는 스크린샷을 첨부

### 5.8 포트 매핑 및 접속 증거

- 컨테이너 실행 시 포트 매핑을 설정한다.
- 브라우저에서 접속한다.
- 주소창과 응답 화면이 보이도록 캡처한다.
- 또는 `curl` 명령의 응답을 기록한다.

```bash
docker run -d -p <host_port>:<container_port> --name <container_name> <image_name>
curl http://localhost:<host_port>
```

### 5.9 바인드 마운트 반영 검증

### 5.10 Docker 볼륨 영속성 검증

- Docker 볼륨을 생성한다.
- 컨테이너에 볼륨을 연결한다.
- 볼륨 내부에 데이터를 저장한다.
- 컨테이너를 삭제한다.
- 새 컨테이너에 같은 볼륨을 연결한다.
- 기존 데이터가 유지되는지 확인한다.
- 생성·연결·검증 명령과 출력 결과를 기록한다.

```bash
docker volume create mydata

docker run -d \
  --name vol-test \
  -v mydata:/data \
  ubuntu sleep infinity

docker exec -it vol-test bash -lc "echo hi > /data/hello.txt && cat /data/hello.txt"

docker rm -f vol-test

docker run -d \
  --name vol-test2 \
  -v mydata:/data \
  ubuntu sleep infinity

docker exec -it vol-test2 bash -lc "cat /data/hello.txt"
```

## 16. 동료 평가 유의사항

- 동료 평가는 캐빈에서 평가자와 피평가자가 함께 대면으로 진행한다.
- 평가 과정과 피드백 작성은 피평가자의 PC에서 진행한다.
- 원격 평가와 여러 평가의 동시 진행은 금지된다.
- 코드 리뷰는 제출한 GitHub Repository의 **Default branch** 내용을 기준으로 진행된다.
- 피평가자는 구현 방법과 기술 선택 이유를 설명할 수 있어야 한다.
- 설명할 수 없는 코드나 단순히 “AI가 작성했다”는 답변은 인정되지 않을 수 있다.
- 평가자는 체크리스트만 확인하지 말고 실제 명령 실행, 로그, 접속, 데이터 유지 여부를 검증한다.
- 피드백에는 확인한 기능, 코드 또는 명령, 문제 해결 과정, 학습한 내용을 구체적으로 작성한다.
